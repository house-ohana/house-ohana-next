## 7. 「分からない」が多い場合の収束ロジック（判定順序を明記）

```ts
// 前提: この判定はC1〜C8すべてに回答が揃った後にのみ行う。
// 支援枝・実家枝の isApplicable も、この関数を内部で呼び出す形で実装済み。
function isMaximallyUncertain(answers: PostAnswers): boolean {
  return (
    answers.c4 === "unknown" &&
    answers.c6 === "unknown" &&
    answers.c7 === "unknown" &&
    answers.c8 === "unknown"
  );
}

// 支援枝のゲート（C4が既知でも、収束条件が成立していれば出さない）
function isSupportBranchApplicable(answers: PostAnswers): boolean {
  if (isMaximallyUncertain(answers)) return false;
  return answers.c4 === "partly_arranged" || answers.c4 === "not_arranged" || answers.c4 === "unknown";
}

// 実家枝のゲート
function isHomeBranchApplicable(answers: PostAnswers): boolean {
  if (isMaximallyUncertain(answers)) return false;
  return answers.c6 !== "no_home_issue" && answers.c6 !== "unknown";
}
```

C4のみ「分からない」で、C6・C7・C8のいずれかが具体的な値であれば収束条件は成立せず、支援枝は通常どおり判定される（＝「C4が分からない」ことそのものは支援枝を出す理由の一つであり、収束条件はその例外扱いとして機能する）。

## 13. 想定リスク

以下はPhase2設計時に想定したリスクと対応方針の記録である。現在の未対応事項を意味するものではない。

| リスク | 内容 | 対応方針 |
|---|---|---|
| CT1の文言分岐漏れ | H1の値ごとにCT1のtitle/leadを出し分ける実装で、想定外のH1値（keep_for_now/undecidedなど、本来CT1が非表示のはずの値）が来た場合のフォールバック文言が必要 | H1がsell/rent/demolish以外のときはCT1自体が非該当（isApplicable=false）なので到達しない設計を維持し、念のためdefault文言を売却向けに設定しておく |
| `homeActionExpected`再構成時の回帰 | 3変数のORへ書き換える際の書き損じ | 既存の回帰テスト（firstAction.id等のスナップショット）で検出する |
| 選択肢追加によるURL長のわずかな増加 | 影響は軽微 | 対応不要 |
| S1統合による情報の粗さ | 「申請中」「未申請」を分離してもなお、要介護認定の詳細な段階までは拾えない | Phase4で知識カードを作る際に必要なら再検討する |
