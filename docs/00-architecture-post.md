## 2. システム全体のデータフロー

```
質問定義 questions.ts
  ↓
利用者回答 PostAnswers / PostValidAnswers
  ↓
URL検証・復号 schema.ts
  ↓
内部変数 variables.ts
  ↓
行動・判定ロジック actions.ts / decisions.ts / insights.ts / contacts.ts / selfHelp.ts
  ↓
診断結果 PostResult
  ↓
成果物生成 artifacts/*
  ↓
知識カード選択 knowledgeCards/*（Phase4以降）
  ↓
画面表示 DiagnosisResultSections.tsx / 専門家向け表示 / 印刷表示
```

**重要原則**

- 質問層は、表示文章を決めない
- 変数層は、利用者向け文章を持たない
- 判定層は、UIレイアウトを持たない
- 成果物層は、診断優先順位を変更しない
- 成果物層・表示層は、判定を独自に再実装しない（生の回答値から条件を再計算しない。変数層の確定フラグ・既存判定結果を読むだけとする）
- 医療・法律・税務の断定的判定、本人能力の断定、特定商品・サービスの推奨は、判定層・成果物層・知識カード層・表示層のいずれの出力にも含めない（第2-1項）

### 2-1. 全出力層に共通する士業境界

「House OHANAが決めないこと」を、実装上の禁止として全出力層へ適用する。以下は判定層・成果物層・知識カード層・表示層のどこでも出力しない。

- 自宅か施設か、どの施設か等の居住方針の決定
- 実家を売る/貸す/解体するの決定、特定の不動産会社・保険商品の推奨
- 医療・介護の内容の判断
- 法律・税務・登記上の適用確定、本人の判断能力の断定
- 「危険」「問題」「不適切」等の評価・判定表現

各層は事実の整理・提示にとどめ、判断は利用者・家族・有資格の専門家に委ねる。

## 3. 層ごとの責務

### 3-1. 質問層
対象：questions.ts / types.ts / DiagnosisWizard.tsx
責務：質問文／選択肢／条件付き質問／戻る操作時の依存回答削除／回答完了判定
禁止：制度説明／結果文章／専門家推奨／税務・法律上の判定

### 3-2. URL・検証層
対象：schema.ts / mode.ts
責務：回答コードの検証／バージョン互換性／不正URLの拒否／正規URL生成
禁止：回答の推測変換／旧バージョンを新ルールで勝手に再解釈／自由記述や個人情報のURL保存

### 3-3. 内部変数層
対象：variables.ts
責務：回答を判定用フラグへ変換／複雑な条件を一か所へ集約／純粋関数として動作。下位層（成果物層・表示層）が参照する条件フラグは、原則ここで確定させる。
禁止：利用者向け文章／UI／出典／優先順位の直接決定

### 3-4. 行動・判定層
対象：actions.ts / decisions.ts / insights.ts / contacts.ts / selfHelp.ts / consultation.ts / logic.ts
責務：最初の行動／次の行動／後回し／注意事項／相談先／表示候補／優先順位／重複排除
禁止：UIレイアウト／印刷CSS／成果物用の大量なif文／専門家向けサマリーの直接生成／医療・法律・税務の断定的判定の出力（第2-1項）

### 3-5. 成果物層
Phase3で追加する。対象：`lib/diagnosis/post/artifacts/`
責務：家族会議メモ／相談前準備リスト／専門家向け相談サマリー／今回整理できたこと／未確認事項／印刷用データ

成果物層は、既存結果を加工するだけとする。入力として読んでよいのは「回答事実」「変数層の確定フラグ」「既存の判定結果（firstAction等）」の3つのみ。表示条件・分岐（実家の有無、意向、支援状況、unknown/undecided/not_confirmed 等）は変数層フラグを読んで決め、生の回答値から再判定しない。未確認/確認済みの判定は変数層（または判定層）で確定し、成果物層は組み立てるだけとする。

ただし、単一の回答値をそのまま固定文言テーブルで参照する（例：`answers.c1`の値によって表示する書類候補を切り替える）ことは「回答事実」の利用であり、複数条件を組み合わせた判定の再実装には当たらない。禁止されるのは、actions.ts/decisions.ts等が持つ複合的な条件式を成果物層で複製することである。

禁止：firstActionの変更／優先順位の変更／新しい医学・法律・税務判定／質問追加／断定・評価表現や士業判断の確定（第2-1項）／必要フラグが変数層に無いときに成果物層で判定を自作すること（この場合は停止して確認）

### 3-6. 知識カード層
Phase4で追加する。対象：`lib/diagnosis/post/knowledgeCards/`

推奨構成：
```
knowledgeCards/
  content/  discharge.ts care.ts work.ts money.ts facility.ts insurance.ts home.ts legal.ts tax.ts
  rules/    discharge.ts care.ts work.ts money.ts facility.ts insurance.ts home.ts legal.ts tax.ts
  selector.ts
  freshness.ts
  types.ts
```

責務：公的一次情報の短文化／表示条件／除外条件／出典／確認日／鮮度管理
禁止：リアルタイム検索結果を無検証で表示／相続後カードをm=postへ混入／本文と判定ルールの混在／制度・税務の適用を断定する表現（第2-1項。カードは一次情報の要約＋出典＋確認日の提示にとどめる）

### 3-7. 表示層
対象：DiagnosisResultSections.tsx / DiagnosisProfessionalSummary.tsx / DiagnosisPrintActions.tsx
責務：レイアウト／余白／色／折りたたみ／専門家向け表示／印刷ボタン
禁止：回答値を直接見て判定を再実装／UI内の複雑なif文／独自の優先順位変更

## 5. Phase3の位置づけ

Phase3は「知識カードを増やすPhase」ではない。

**Phase3で行うこと**：既存回答を家族会議メモへ変換／相談前準備リストを生成／専門家向け相談サマリーを生成／未確認事項を抽出／印刷できる形へ整える

**Phase3で行わないこと**：新しい質問／新しい制度判定／公的情報カードの量産／ケース履歴保存／AI要約

（具体仕様は下位の「Phase3指示書 v1.1」に従う。）

Phase3終了後は成果物の実利用を優先し、知識カード追加は行わない。知識カードは、成果物構造が安定してから追加する（第5-2章・第5-3章）。

### 5-2. Phase3.5 実利用・有用性検証（新設）

Phase3終了後、知識カード追加へ進まない。まず、成果物が現場で利用できるかを検証する。

目的：
- 家族が理解できるか
- 家族会議で利用できるか
- 専門家へそのまま渡せるか
- 質問不足があるか
- 不要な成果物があるか
- 文章量が適切か
- 利用者が迷わず読めるか
- 相談につながる品質になっているか

**推奨確認件数**（目安。品質改善が目的であり、件数達成自体が目的ではない）

| 対象 | 件数目安 |
|---|---|
| 家族利用 | 10件以上 |
| ケアマネジャー | 3件以上 |
| 病院MSW | 3件以上 |
| 不動産実務者 | 3件以上 |
| 司法書士 | 2件以上 |
| FP | 2件以上 |

### 5-3. Phase4開始条件（新設）

次の条件をすべて満たした場合のみPhase4へ着手する。

- Phase3成果物が実利用された
- 重大なUI改善点が残っていない
- 成果物構成が概ね固まった
- 質問不足が整理された
- 専門家レビューを受けた
- ユーザー承認がある

Phase4は、成果物が安定してから開始する。

## 8. バージョン管理

以下を分離する。

- POST_SCHEMA_VERSION
- RESULT_LOGIC_VERSION
- ARTIFACT_VERSION
- KNOWLEDGE_RULE_VERSION
- GUIDANCE_CONTENT_VERSION

URLへ載せるのは、原則として回答互換性に関わる POST_SCHEMA_VERSION のみ。文章・出典・UI変更だけでURLを無効化しない。

### 8-1. どの定数をいつ上げるか

各定数の変更を含むPRで、該当定数を上げる。判断基準：

| 変更内容 | 上げる定数 | URL無効化 |
|---|---|---|
| 質問・選択肢・回答コード・URL互換に関わる変更 | POST_SCHEMA_VERSION | する |
| firstAction・優先順位・分岐など判定ロジックの変更 | RESULT_LOGIC_VERSION | しない |
| 成果物（メモ・準備・サマリー等）の構成・生成の変更 | ARTIFACT_VERSION | しない |
| 知識カードの表示/除外条件・ルールの変更 | KNOWLEDGE_RULE_VERSION | しない |
| 知識カードや案内の本文・出典・確認日など文言のみの変更 | GUIDANCE_CONTENT_VERSION | しない |

KNOWLEDGE_RULE_VERSION と GUIDANCE_CONTENT_VERSION の境界：表示するか否かの条件が変われば rule、出す内容の文言だけが変われば content。迷う場合は rule 側を上げる（表示条件に影響しうるため安全側）。

### 8-2. ADR（Architecture Decision Record）（新設）

`docs/adr/` フォルダへ、以下のADRを置く。

```
docs/
  adr/
    ADR-001  成果物層は判定しない
    ADR-002  URLへ個人情報を保存しない
    ADR-003  知識カードは一次情報のみ
    ADR-004  知識カードは成果物の実利用後に追加する
```

ADRは「なぜこの設計にしたのか」を残す文書である。将来の開発者・AIは、ADRを変更理由の唯一の正本として扱う。ADRの新規作成自体は、各Phase指示書の承認フローに従って行う（本項は置き場所のルールのみを定める）。

## 9. テスト責務

- 質問・URL：回答コード／分岐／依存回答削除／旧URL拒否
- 変数：回答からフラグへの変換
- 判定：firstAction ID／nextAction ID／カードID／優先順位／重複排除
- 成果物：家族会議項目ID／準備項目ID／サマリー項目ID／未確認項目ID／最大件数／条件外項目の非表示／サマリー値変換の正確性（未定・調整中の回答が「決定済み」「確定」等に化けないこと）／分岐が変数層フラグ由来であること（同一フラグに対し回答表現差で結果集合が変わらない）
- 知識カード（Phase4）：カードID／表示・除外条件の発火／出典URLの有効性／確認日が更新サイクル内であること／鮮度切れカードの非表示または警告
- 表示：スマホ／折りたたみ／印刷／横スクロール／空見出し

文章完全一致を主要な合否条件にしない。ただし、上記の値変換・出典・鮮度は内容の正確性に直結するため、代表的な回答集合・カードでの正当性検証を行う。

## 10. 変更時の原則

新しい機能を追加する前に、必ず以下を答える。

1. どの層の責務か
2. 既存層で対応できない理由
3. どのファイルへ置くか
4. 既存ロジックへ影響するか
5. どのテストを追加するか
6. 将来削除・差替えできるか

責務が決まらない機能は実装しない。必要な判定フラグが変数層に無い場合は、成果物層・表示層で自作せず、変数層への追加として設計する（第3-5項）。

知識カードは、成果物が現場で利用され、有用性が確認された後に追加する。成果物が十分に検証されていない段階では、知識カードを量産しない。現場で不要と判明したカードは実装しない。

## 11. 次に行うこと（全体工程の見取り図）

本章は工程の順序を示すもので、本文書単独での着手指示ではない（第0章）。

Phase3 Step3は完了済みである。次はPhase3.5の実利用・有用性検証を継続し、その中でPhase4.1の最小知識カード実証を進める。Phase4.2へは自動的に進まない。

```
Phase3（成果物生成）
  ↓
実利用（Phase3.5）
  ↓
成果物改善
  ↓
ユーザー承認
  ↓
Phase4（知識カードライブラリ）
```

Phase3終了時点では、知識カード実装へ進まない。Phase3.5完了後にPhase4へ進む。
