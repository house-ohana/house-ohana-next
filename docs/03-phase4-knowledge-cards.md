## 1. House OHANAにおける知識カードの役割

知識カードは、House OHANAの中で次の性格を持つ。

- **制度を網羅的に説明するためのものではない**。関連する公的制度・手続のうち、今回の回答から見て関係が深いものだけを、短く提示する。
- **診断結果を上書きしない**。`firstAction`・`nextActions`・`decideNow`・`decideLater`など、既存の判定層が導いた結果を、知識カードが書き換える・覆すことはない。
- **家族が「誰へ何を聞くか」を理解するための補足情報である**。ただしその役割は、①まだ問題だと気づいていない崖を示し、②その崖に対する確認項目を整理し、③既存の相談先へ接続する、という順序で広がる。制度の詳細な適用可否を家族自身に判断させるためのものではなく、次に相談する専門家・窓口に何を尋ねればよいかを整理する補助である。
- **利用者がまだ問題だと認識していない論点を示す**。すでに気づいている事実の繰り返し（`confirmedFacts`・`unknownItems`の再掲）や、次の行動の重複案内（`actions`・`contacts`の再掲）を主目的としない。
- **行動指示の前に「なぜ今確認が必要か」を説明する**。何をすべきかだけでなく、後回しにするとどうなるかという背景を示す。
- **制度の網羅ではなく、後戻りしにくい崖を限定して示す**。件数を絞り、重要度の高いものだけを提示する。
- **既存の`actions`や`contacts`を置き換えない**。次にすべき行動・相談先の決定は既存層の責務のままとし、知識カードはそこへ接続するにとどまる。
- **既存結果を繰り返すだけのカードは作らない**。`confirmedFacts`・`unknownItems`・`decisions`等ですでに示されている内容をそのまま言い換えただけのカードは追加しない。
- **専門家の代わりではなく、専門家へつなぐためのもの**。カードの本文が専門家の助言に代わることはない。
- **不安を増やすのではなく、次の一歩を整理する**。網羅性や警告の強さを優先せず、今できる次の一歩が分かることを優先する。
- **カード選択は弱い判断であり、誤発火には誤案内コストがある**。カードの表示条件は、既存の判定層と同様に確定的なルールで動くが、それでも「本来関係ないカードが出る」ことは家族の混乱・誤解を招くコストを伴う。表示条件は保守的に設計する。
- **House OHANAは制度適用、方針、能力、最適解を決めない**。アーキテクチャ仕様書第2-1項の士業境界を、知識カード層でも徹底する。「この制度が使えます」「この方針が最適です」という断定は行わない。
- **固定・レビュー済み本文のみ使用し、実行時AI生成を行わない**。カード本文はあらかじめ人が作成・確認した固定文のみを使用する。生成AIによるその場での文章生成は行わない。

## 2. Phase4の目的・実装範囲・対象外

**目的**：Phase4は、公的一次情報にもとづく知識カードを、House OHANAの結果画面へ追加・運用していく層である。

**Phase4.1の目的**：Phase4.1は、相談窓口そのものを説明するカードを配置することを目的としない。回答から、利用者がまだ見落としやすい崖を最大2件示し、既存の行動・相談先へ接続できるかを検証することを目的とする。知識カードは、制度紹介・窓口紹介・既存`contacts`の再掲を主目的としない。主目的は、まだ問題だと気づいていない未確認事項を、後戻りしにくくなる前に示すことである。

**実装範囲（段階的な拡張）**：

- **Phase4.1**：以下3カードで、知識カード層の基盤（content／matcher／reasons／selector／freshness／UI／tests の責務分離）と、「崖を示す」という成果物そのものの有用性を検証する。
- **Phase4.2以降**：Phase4.1の検証結果を踏まえ、必要と判断された崖カードを追加していく。Phase4.2以降の対象カード・優先順位は、Phase4.1完了後に別途定める。

### Phase4.1対象カード（3件）

**Card A（仮ID：`discharge_support_start_gap`）**
利用者向けタイトル：「退院後の支援は、退院日と同じ日に始まるとは限りません」
示す崖：退院後に必要な支援が、退院当日からすべて始まるとは限らない。
確認項目の方向性：退院当日の移動／最初の数日を誰が支えるか／医療・介護・生活支援の開始日／未決定事項の担当者と確認期限。
前提としないこと：「退院日が決まっていること」を必須前提にしない。退院日確定の有無を表す新規Variablesは、Phase4.1では追加しない方針とする。

**Card B（仮ID：`transition_monthly_cash_gap`）**
利用者向けタイトル：「費用の総額が見えても、家族の持ち出しが始まる月は別です」
示す崖：医療費や施設費の総額だけでなく、毎月続く支出・一時的に重なる支出・残る住まいの維持費・家族の立替えが重なる時期を確認しないと、家族負担の開始時期を見落とす可能性がある。
判定しないこと：費用不足、制度適用、保険適用、支払能力の判定は行わない。

**Card C（仮ID：`home_ownership_intent_gap`）**
利用者向けタイトル：「家の方針が決まっても、名義と本人の意向が揃っているとは限りません」
示す崖：売却・賃貸・解体等の方向性と、名義・共有者・本人の理解や意向・契約前に確認すべき相手は、別に確認する必要がある。
判定しないこと：本人の判断能力、契約の有効性、売却・賃貸・解体の適否は判定しない。

**Phase4.1時点での対象外領域**：高額療養費、高額介護サービス費、税務、法律、不動産、保険、相続、空き家、仕事と介護という制度・分野そのものの説明。これらはPhase4.2以降で改めて要否を判断する対象であり、Phase4.1では扱わない。

**Phase4.2以降の候補（参考。Phase4.1の実装対象には含めない）**：「家族の支援が一人へ集中する崖」は、Phase4.2以降の有力候補として記録する。

**やらないこと**：

- 対象外領域の死コード・無効カード・先行テストを、Phase4.1の時点で作らない。
- 質問の追加、URLスキーマの変更、既存診断ロジック（`actions.ts`／`decisions.ts`／`insights.ts`／`contacts.ts`／`selfHelp.ts`／`consultation.ts`）の変更は、知識カード層の責務ではない。
- カードの表示条件に必要な回答データが変数層に存在しない場合、知識カード層で判定を自作しない。質問の追加や`variables.ts`への変数追加が必要であれば、それは知識カード層とは別の変更として、実装を止めてユーザーに確認する。

### 最大表示件数

Phase4.1では最大2件とする。0件でもよく、その場合は空見出しを表示しない。件数の適用はselectorの責務とし（第4章）、UIは独自に件数調整しない。

該当するカードが2件を超える場合の優先順位は、以下の原則にもとづく。具体的なrank値と発火条件は、本書ではなくPhase4.1実装指示書で定める。

- 時間制約のある生活上の崖を優先する
- 後戻りしにくい契約・資産上の崖を次に考慮する
- 金銭上の崖は、緊急性を示すフラグに応じて順位を上げる

## 3. 全体アーキテクチャとの接続

```
Questions
  ↓
Answers
  ↓
Schema
  ↓
Variables
  ↓
Decision Logic
  ↓
PostResult
  ↓
Artifacts
  ↓
Knowledge Cards
  ↓
Result UI
```

各層の接続にあたり、以下を明記する。

- **Questionsはカード本文を決めない**。質問層（`questions.ts`）は質問文・選択肢のみを持ち、知識カードの表示文言・表示条件には関与しない。
- **Variablesは利用者向け文章を持たない**。変数層（`variables.ts`）はカード発火判定に使えるフラグを提供するが、カードの文言そのものは持たない。
- **Decision Logicはカード表示を理由に優先順位を変更しない**。判定層（`actions.ts`等）の`firstAction`・優先順位の決定ロジックは、知識カードの有無・表示状況によって左右されない。
- **Artifactsはカードを選ばない**。Phase3成果物層（`buildConfirmedFacts`／`buildUnknownItems`／`buildPostArtifacts`）は知識カードの選定・表示条件判定を行わない。知識カード層とPhase3成果物層は独立した層である。
- **Knowledge Cardsは既存診断・成果物を変更しない**。知識カード層は次のいずれも変更しない。
  - `firstAction`を変更しない
  - `nextActions`を変更しない
  - `decisions`（`decideNow`／`decideLater`）を変更しない
  - `confirmedFacts`を変更しない
  - `unknownItems`を非表示にしない
  - `contacts`を置き換えない
  - `selfHelp`を置き換えない
  - `consultation`を変更しない

  各層の役割は次のとおり分担する。

  | 層 | 役割 |
  |---|---|
  | `confirmedFacts` | 確認できている事実 |
  | `unknownItems` | 確認できていない状態 |
  | `knowledgeCards` | 未確認のまま進む際の見落としやすい崖 |
  | `actions` | 次に行うこと |
  | `contacts` | 誰に確認するか |
- **UIは回答値やVariablesを直接見てカードを再選択しない**。表示層（`DiagnosisResultSections.tsx`等）は、知識カード層のselectorが出力した結果をそのまま描画するだけで、`answers`や`variables`を直接参照してカードの要否を再判定しない。
- **selectorの出力だけを描画する**。UIが参照してよいのは、selectorが返す確定済みのカードリストのみである。
- **PostResultやURL互換性への接続方針は下位実装指示で定める**。`PostResult`へどのフィールドとしてカード結果を渡すか、URLへの影響有無の具体的な設計は、本書ではなくPhase4.1指示書側で定める。
- **POST_SCHEMA_VERSIONは質問・回答コードが変わらない限り上げない**。知識カードの追加・変更自体は質問構造・回答コードに影響しないため、`POST_SCHEMA_VERSION`を上げる理由にはならない（アーキテクチャ仕様書第8-1項の基準に従う）。

## 4. 知識カード層の責務分離

知識カード層は、単一の大きなモジュールではなく、以下の7つの責務に分離する。

### content（カード本文）

**定義**：

- id
- title
- cliff（見落としやすい崖の説明）
- checkItems（確認する項目）
- linkedContactIds（既存`PostResult.contacts`との接続候補を示す参照値。新しい相談先情報を複製するためのものではない）
- sources（出典）
- verifiedAt（確認日）
- reviewBy（次回レビュー予定日）

**contentは次を持たない**：

- 表示条件
- reasonId
- rank
- urgency
- whyNow
- action
- contact
- questionToAsk

**なぜこの層へ置くのか**：カードの文言・出典・鮮度情報は、表示するかどうかの判定ロジックとは独立して管理・レビューできる必要がある。文言だけを更新する変更と、表示条件を変える変更を分離することで、`GUIDANCE_CONTENT_VERSION`と`KNOWLEDGE_RULE_VERSION`（アーキテクチャ仕様書第8-1項）の区別が保てる。`action`／`contact`／`questionToAsk`は既存の`actions.ts`・`contacts.ts`が持つ情報と重複するため、contentへ複製しない（`linkedContactIds`による参照にとどめる）。`whyNow`（今回なぜこのカードが表示されたか）は回答によって変わる文言であり、固定文であるcontentではなくreasonsの責務とする。

**してはいけないこと**：contentは表示条件（発火条件・除外条件）を持たない。「いつ表示するか」はmatcherの責務であり、contentに条件分岐を書かない。

### matcher（発火判定）

**定義**：

- 発火条件
- 除外条件
- reasonId
- urgency
- rank
- 本文を持たない
- matched判定と理由を分離しない

**なぜこの層へ置くのか**：どの回答パターンでカードを出すかという判定は、contentの文言とは独立して変更・テストできる必要がある。またmatcherは「該当する（matched）」という判定と「なぜ該当したか（reasonId）」を同時に返すことで、reasons層が発火条件を再判定せずに済むようにする。

**してはいけないこと**：matcherはカード本文（タイトル・coreFact等）を持たない。判定結果（matched）と理由（reasonId）を別々の場所で管理しない。

### reasons（表示理由の文言化）

**定義**：

- reasonIdから、利用者向け名称「whyNow」（今回なぜこのカードが表示されたか）の固定文への変換
- matcherが返せるreasonIdと完全一致

**reasonsは次を行わない**：

- 発火条件を再判定しない
- 生回答を参照しない
- content本文を持たない
- `actions`や`contacts`を生成しない

**なぜこの層へ置くのか**：「なぜこのカードが表示されたか」を家族に伝える文言は、matcherの発火条件そのものとは別に、文言としての調整（言い回しの改善等）が発生しうる。reasonsを独立させることで、発火条件を変えずに説明文だけを調整できる。

**してはいけないこと**：reasonsはmatcherが判定した発火条件を再判定しない。reasonsが持つ`reasonId`の集合は、matcherが返しうる`reasonId`の集合と完全一致させ、両者がずれないようにする。生の回答値（`answers`）を直接参照して新たな判定・分岐を行わない。

### selector（統合・整列）

**定義**：

- matcher結果を集める
- enabled状態を確認する
- rank順に並べる
- 最大件数を適用する
- 発火条件を書かない
- 本文を書かない

**なぜこの層へ置くのか**：複数のカードのmatcher結果を集約し、表示可否・順序・件数上限を決める処理は、個々のカードの発火条件やcontentとは別の、横断的な責務である。Phase3の`buildPostArtifacts`が`buildConfirmedFacts`／`buildUnknownItems`を束ねるだけのオーケストレータであるのと同じ位置づけである。

**してはいけないこと**：selectorは個々のカードの発火条件（それはmatcherの責務）やカード本文（それはcontentの責務）を持たない。selector自身が新しい判定条件を書かない。

### freshness（鮮度管理）

**定義**：

- verifiedAt／reviewByの内部管理
- reviewBy超過だけで自動非表示にしない
- リンク死活・内容不一致は運用で確認する
- 利用者向け制度判定をしない

**なぜこの層へ置くのか**：出典の鮮度（確認日・レビュー予定日）は、カードの発火条件や本文とは異なる管理軸であり、独立して追跡できる必要がある。

**してはいけないこと**：`reviewBy`を過ぎたことだけを理由に、自動でカードを非表示にする判定をfreshness層に持たせない（自動非表示にするかどうかの運用判断は別途定める）。リンク切れや内容不一致の検知は、freshness層のロジックではなく運用上の確認作業に委ねる。freshnessは制度の適用可否を利用者向けに判定しない。

### UI（表示）

**定義**：

- selector結果をそのまま描画
- 回答値やVariablesを参照しない
- 商用サービス導線と視覚的に分離する
- urgencyをPhase4.1で色分けに使わない

**なぜこの層へ置くのか**：表示層は、アーキテクチャ仕様書第3-7項の既存原則（「回答値を直接見て判定を再実装しない」）を知識カード層でも踏襲する。selectorが確定させた結果を描画するだけにすることで、UIに判定ロジックが紛れ込むことを防ぐ。

**してはいけないこと**：UIはselectorを経由せず`answers`／`variables`を直接見てカードの要否を判定しない。House OHANAの相談・問い合わせ導線など商用サービスの導線と、知識カードの表示領域を視覚的に混在させない。`urgency`（matcherが持つ緊急度情報）を、Phase4.1の時点では色分け等の強調表現に用いない（アーキテクチャ仕様書のブランド制約に従い、赤・黄色等の新しい強調色を追加しないため）。

### tests（テスト）

**定義**：

- matcher
- reasons
- selector
- freshness
- content
- 回帰
の責務を分離する

**なぜこの層へ置くのか**：content／matcher／reasons／selector／freshnessという責務分離を、テストの構成でも維持することで、ある層の変更が意図せず他の層の挙動を変えていないかを検証できる。

**してはいけないこと**：1つのテストファイル・1つのテストケースに複数層の責務（例：発火条件の正しさと文言の正しさ）を混在させない。既存のPhase1〜Phase3の回帰テスト（156件）を壊さないことを、知識カード層のテストとは別に維持する。

- **Phase4.1対象カードを差し替え**：入退院支援・地域包括支援センター・ケアマネジャーという相談窓口型3カードを削除し、`discharge_support_start_gap`（退院後支援の開始日ギャップ）／`transition_monthly_cash_gap`（費用の月次ギャップ）／`home_ownership_intent_gap`（名義・本人意向ギャップ）という崖提示型3カードへ変更した（第2章）。
- **第1章（役割）を拡張**：「利用者がまだ問題だと認識していない論点を示す」等5点を追加し、「誰へ何を聞くかを理解する補足情報」という既存記述を、崖を示す→確認項目を整理する→既存相談先へ接続する、という順序へ広げた。
- **第4章content責務を変更**：`action`／`contact`／`questionToAsk`をcontentから削除し（既存`actions.ts`・`contacts.ts`との重複防止）、`id`／`title`／`cliff`／`checkItems`／`linkedContactIds`／`sources`／`verifiedAt`／`reviewBy`へ変更した。`whyNow`はreasonsの責務であることを明記した。
- **第4章reasons責務を明確化**：利用者向け名称を`whyNow`とし、発火条件の再判定・生回答の参照・content本文の保持・`actions`/`contacts`の生成のいずれも行わないことを明記した。
- **第3章へ既存結果層との境界を追記**：`firstAction`／`nextActions`／`decisions`／`confirmedFacts`／`unknownItems`／`contacts`／`selfHelp`／`consultation`を変更しないことを列挙し、`confirmedFacts`／`unknownItems`／`knowledgeCards`／`actions`／`contacts`の役割分担表を追加した。
- **表示件数の原則を追加**：Phase4.1の最大表示件数を2件とし、時間制約のある生活上の崖→契約・資産上の崖→金銭上の崖（緊急性フラグに応じて順位を上げる）という優先原則を第2章に記載した。具体的なrank値・発火条件は本書に記載せず、Phase4.1実装指示書に委ねる。
- **Phase4.2以降の候補を記録**：「家族の支援が一人へ集中する崖」をPhase4.2以降の候補として第2章に記載した（Phase4.1の実装対象には含めない）。
- matcher／selector／freshness／UI／testsの責務定義（第4章）は、カードの内容に依存しない構造原則のため変更していない。
